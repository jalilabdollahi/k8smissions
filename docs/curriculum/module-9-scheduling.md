# Module 9: scheduling

Advanced module about the scheduler itself: why a pod lands where it does, why it stays Pending, and how to change that. Every level is proven by where pods actually run (`spec.nodeName`, events from the scheduler, preemption, allocated resources), never by a field. Add-on: `metrics-server`, only in the levels that list it in `requires` (l17; l10 may use it). Overlap decisions: module 1 owns "Pending from requests" and the basic `nodeSelector`, module 5 owns taints and affinity as isolation and PriorityClass for critical pods, module 6 owns node conditions, module 2 owns `maxSurge`. So the levels here are about scheduler mechanics: toleration timing, AND/OR semantics of affinity terms, label selectors inside affinity and spread rules, fragmentation, hidden request inflation (pod overhead, init containers), preemption rules, extra schedulers, extended resources, hostPorts. Node names are always looked up (`kubectl get nodes -l '!node-role.kubernetes.io/control-plane'`); levels label nodes with `zone=`, `disktype=`, `lifecycle=`, `pool=` and taint with custom keys only. Any level that sizes filler pods computes node free resources at setup time with kubectl (allocatable minus the sum of requests of pods on the node), so it works on any host.

## Notes

- Images: `registry.k8s.io/pause:3.10`, `busybox:1.37`, `nginx:1.27-alpine`, `python:3.12-alpine`, `registry.k8s.io/kube-scheduler:v1.36.x` for l12, `registry.k8s.io/descheduler/descheduler:<tag>` for l9. Verify every tag with `docker manifest inspect` first.
- Sizing: levels that fill nodes (l5, l8, l13, l15, l17) compute free CPU/memory per worker at setup from allocatable minus the requests of pods already on the node, and size requests as fractions of that. Never hard-code Gi/m values.
- l9 `descheduler-config`: the real Descheduler runs as a CronJob (schedule every minute, `concurrencyPolicy: Forbid`) with ServiceAccount, ClusterRole and policy ConfigMap created from `broken.yaml` (all labelled managed). `--v=4` so evictions appear in logs. If no descheduler tag runs cleanly against Kubernetes 1.36, fall back to a manual rebalancing scenario: pods piled on one worker, a `rebalancer` CronJob (python:3.12-alpine, Eviction API) with a threshold ConfigMap that is wrong in two ways, and the same validator.
- l10 `allocatable-vs-capacity`: kind sets no kubelet reservations, so capacity equals allocatable and the literal slug cannot be shown. The reinterpretation uses a RuntimeClass with pod overhead (handler `runc`, which exists in kind's containerd), a real scheduler input that makes "what you asked" differ from "what is reserved". RuntimeClass objects are created by `broken.yaml` with the managed label.
- l11 `extended-resource`: setup advertises capacity with `kubectl patch node <n> --subresource=status --type=json -p '[{"op":"add","path":"/status/capacity/example.com~1fpgas","value":"2"}]'`. This is real scheduler behaviour, but node status is not cleared by the engine reset. Engine request: reset.py should remove any non-standard `status.capacity` entries (domain not kubernetes.io) at level start, otherwise the resource leaks into later levels.
- l12 `scheduler-name`: the second scheduler runs as a pod in `$NS` with `--config` (KubeSchedulerConfiguration, profile `ml-scheduler`, `MostAllocated` in NodeResourcesFit), `--leader-elect=false`, its own ServiceAccount bound to ClusterRoles `system:kube-scheduler` and `system:volume-scheduler` (ClusterRoleBinding labelled managed), in-cluster credentials (no kubeconfig). Verify startup time and set `settle_seconds` accordingly.
- l14 `node-pressure`: real memory or disk pressure on a kind node is unsafe (it affects the host). The level keeps the theme (kubelet evicting pods for resource usage the scheduler never saw) with ephemeral-storage limit enforcement, which is deterministic. Evicted pods remain as Failed objects and are the visible evidence.
- l16 `resource-class`: DRA (`resource.k8s.io/v1`) is GA in 1.36 but kind has no DRA driver, so there is no kubelet plugin and the pod cannot reach Running. ResourceSlices are written by hand with a made-up driver name (allowed for a cluster admin); the scheduler's DynamicResources plugin really allocates from them. `ResourceClass` was replaced by `DeviceClass` in the API. Confirm with `kubectl api-resources --api-group=resource.k8s.io` while writing the level. The validator stops at scheduler allocation by design.
- l13 `pending-deadlock`: the old topic (a webhook that blocks all pods) belongs to module 10. Here the deadlock is a real gang-scheduling one. Setup creates both Jobs with `parallelism: 2`, waits for the 4 pods, then patches both to 3 so the interleaving is deterministic. The barrier is a loop on a headless Service with `publishNotReadyAddresses: true` counting addresses (a Pending pod has none).
- Add-on: l17 `requires: ["metrics-server"]`; l10 may add it. No other add-ons.
