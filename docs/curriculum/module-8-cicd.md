# Module 8: cicd

Tekton Pipelines v1.18.0 only (no Triggers, no Dashboard, no `tkn` assumed): players use `kubectl` on Task, Pipeline, TaskRun and PipelineRun, plus pod logs (`kubectl logs <pod> -c step-<name>`). The module walks from admission-time rejections (workspaces, params), through step and result mechanics, credentials, `finally` and gates, to RBAC for pipeline ServiceAccounts and a three-fault finale. Add-on: `tekton` for every level. Overlap decisions: module 5 owns RBAC basics, so levels 8 and 14 are only about what a pipeline ServiceAccount needs (cross-namespace deploy, creating and waiting on runs, least privilege); module 2 owns canary and rollback mechanics with plain objects, so levels 11 and 12 are about the pipeline logic that automates them (gate and abort conditions); module 4 owns volumes, so level 15 is about concurrent runs sharing one claim. Module 8 is advanced overall; the early levels are intermediate so the first Tekton contact is gentle.

## Notes

**Patterns for validators.** Pattern A (definition levels): the fix is in a Task or Pipeline, so `validate.sh` creates its own PipelineRun(s) with `kubectl create -f -` (generateName `verify-`), waits with `kubectl wait --for=condition=Succeeded` (or polls for Failed when failure is the expected outcome), reads `.status.results` and step logs, and deletes the runs afterwards. Pattern B (run-spec levels, 2, 3, 4, 17): the fix is a new PipelineRun, so the validator accepts any PipelineRun of that Pipeline created after the setup timestamp (stored as an annotation on the Pipeline) other than the seeded failed one. Keep runs small (alpine steps); budget about 45 seconds per run, and set `settle_seconds` generously because the seeded failed run must exist before the broken-state check. Expected-failure checks must verify the right Task failed, not just "the run failed".

**Git fixture.** Levels 4, 10 and 18 reuse the in-cluster Git server defined in `docs/curriculum/module-7-gitops.md` (namespace `gitops-git`, Service `gitserver`, BusyBox `httpd` with `git http-backend`, `alpine/git`). Module 8 additionally uses its private path: repos under `/srv/git/private/<name>.git` are served at `http://gitserver.gitops-git.svc.cluster.local:8080/cgi-bin/git/private/<name>.git` and `httpd.conf` requires basic auth (`ci-bot` with a fixed password) for the `/cgi-bin/git/private/` prefix. Steps clone with `alpine/git`. Spike required before authoring level 4: confirm that Tekton v1.18 credential initialisation (`tekton.dev/git-0`) is picked up by `alpine/git` steps (HOME handling differs by `disable-home-env-overwrite`); if needed the Task sets `HOME` explicitly and the map keeps working.

**Registry fixture (levels 7, 17, 18).** Deployment and Service `registry` in `$NS` (or the level's own namespace), image `registry:2` pinned (use a 2.8.x tag, verify), plain HTTP on port 5000, no TLS. Levels 7 and 18 turn on basic auth with a htpasswd file in a Secret (bcrypt hash precomputed and stored in the level, not generated with a custom image). The push step uses a small stock tool image (candidate `gcr.io/go-containerregistry/crane`, pinned and verified; it appends one tiny layer built by an earlier alpine step, so it needs no pull from the internet) and reads credentials from the docker config that Tekton writes for `tekton.dev/docker-0` Secrets. If no suitable pinned image has a shell and `crane` together, fall back to `curlimages/curl` pushing a single-layer manifest over the registry HTTP API with basic auth and declare that in the level. No pushes are needed outside levels 7, 17 and 18.

**kubectl in steps.** Levels 8, 9, 11, 12, 13, 14, 18 run `kubectl` inside Tasks. The first author picks one pinned image that has both a shell and kubectl (candidates: `registry.k8s.io/kubectl:v1.36.x` if it ships a shell, otherwise a pinned `alpine/k8s` tag) and records it here so every level uses the same one.

**Reinterpreted slugs.**
- `level-10-trigger-binding`: Tekton Triggers are not installed. The theme (webhook payload fields mapped to pipeline params) is kept with a small receiver script in a ConfigMap on `python:3.12-alpine` (stdlib only, creates PipelineRuns through the API with its ServiceAccount token) that applies a `binding.json` mapping, which is real behaviour the receiver runs, not a validator flag.
- `level-11-canary-gate`: Argo Rollouts is not installed. A canary built from two plain Deployments behind one Service, with a Tekton gate Task that samples the Service and decides promote or fail, so the failure is in pipeline logic and wiring.
- `level-12-rollout-abort`: same reinterpretation: the abort is the pipeline's automatic `kubectl rollout undo` after a failed `kubectl rollout status`, wired through `finally` and `when`.
- `level-13-approval-gate`: Tekton has no built-in manual approval. The gate is a Task that polls for an approval object from a listed approver; the level is about cancelling stuck runs and giving gates an expiry rather than flipping the approval, and the validator proves self-approval is still refused.
- `level-16-sidecar-injection`: no Istio or mutating webhook on kind. The theme "a sidecar in the Task pod causes failures" becomes Tekton's own `sidecars` field and the startup race it brings.
- `level-14-pipeline-rbac`: there is no EventListener, so the ServiceAccount's job is creating and waiting on PipelineRuns from a Task.

**First-half author notes (levels 1-9, built and passing).** Fixtures live in `modules/module-8-cicd/_fixtures/` (README, `registry.sh`). Chosen images: `alpine/kubectl:1.36.0` for every kubectl step (sh + kubectl, 94 MB; `registry.k8s.io/kubectl` and `rancher/kubectl` have no shell, `alpine/k8s` is 1.2 GB), `gcr.io/go-containerregistry/crane:debug` pinned by digest for pushes (crane plus busybox shell; no versioned tag has a shell). The Git server is the module 7 fixture, read-only. Deviations from the rows: level 5 validates with its own fresh PVC (a private claim, so earlier player runs cannot warm it) and compares the `resolve` step durations; level 6 states in the objective that the `report` output must still appear in the failing run, so the fix is "keep `onError: continue`, exit with the recorded code" and not simply deleting `onError`; level 7 builds a one-layer image with `crane append` and has the registry credentials wrong twice (host key `registry:5000` and a newline in `auth`); level 9 makes `provision` write its `name` result only at the end of its last step, so a failed `provision` leaves the result missing and a finally Task that references it never starts (the PipelineRun hangs in `Running`), which is how the "results of a failed Task" twist actually behaves in v1.18; the 14 old leaks are removed by the player (one `kubectl delete` by label), the fixed pipeline only cleans its own run; level 8 and 9 runs use SA `deploy-sa` and `default` respectively (default SA gets a Role for pods/services in level 9).

**Second-half author notes (levels 10-18, built and passing).** Deviations from the rows: level 10 has the receiver map `body.head_commit.sha` (GitHub sends `id`) and the validator pushes the older of two commits so a default branch tip cannot pass; level 11 adds Pipeline params `canary-name` and `canary-mode` (ok, error, crash) so the validator can rehearse a good and a broken release in parallel (a serial run does not fit the 90 s validate limit), the second defect is the missing `timeout` on `canary-gate`, and the bad rehearsal is a canary that never becomes ready; level 12 uses the guard value `Error` (never produced) plus `revisionHistoryLimit: 0`, and the validator releases a good tag first so there is a revision to go back to; level 13 makes the gate defect a literal `"0"` passed to the Task instead of the Pipeline param `approval-timeout`, and the validator runs three gates in parallel (no approval, listed approver `maria.k`, unlisted `release-bot`); level 14 needs `create, get, list, watch` on `pipelineruns.tekton.dev`; level 15 uses a build/verify pair with `sleep 12` between them and a `subPath: $(context.pipelineRun.name)` fix; level 16 puts the startup time and port in Task params (`db-startup`, `db-port`) so the validator can rehearse 4, 8 and 12 second sidecars and an unreachable one without editing the Task; level 17 uses separate Task objects (`build-image`, `deploy-image`) and the pod-local `/workspace/digest.txt` as the second layer; level 18: the RoleBinding defect is a subject with the wrong `namespace` (`ci-system`), because the API server rejects a ServiceAccount subject with no namespace, the Git credentials are correct (level 4 owns that mechanism) and the repo's only branch is `master`, and since kind nodes cannot pull from the in-cluster registry the deployed pods run `http-echo` serving `payments-api <pushed digest>`, which the validator compares with the registry's manifest digest. Validators read manifests from the registry with `kubectl exec deploy/registry -- wget` and probe Services through the API-server proxy (`kubectl get --raw /api/v1/namespaces/NS/services/NAME:PORT/proxy/`), so no probe pod is needed.
