# Module 2: workloads

Deployment and controller mechanics: why pods do not appear, rollback by revision, basic probes, basic HPA, rolling-update strategy, PDBs against drains, blue-green and canary with plain Services, StatefulSet identity and its headless Service, ReplicaSet ownership, Deployment pause and CronJob concurrency. Difficulty goes from beginner to advanced. The only add-on is `metrics-server` (l5). Images: `nginx:1.27-alpine`, `hashicorp/http-echo:1.0`, `python:3.12-alpine` with stdlib scripts in ConfigMaps, `busybox:1.36`, `curlimages/curl`.

Overlap decisions: probe tuning beyond the basics (startupProbe, failureThreshold math, probe types) is m6, so l3 and l4 stay with the two classic mistakes (liveness too impatient, no readiness). HPA here is only the "no CPU request" failure; invalid HPAs and GitOps fights are m7/m11. PDB here is "blocks a drain"; m5, m11 and m12 own the other angles. Services stay plain selectors; named ports and EndpointSlices belong to m3. l1 is about why pods never appear (a missing ServiceAccount), not about scaling, so `kubectl scale` is only used by l9. Each level ends with a different fix, and every validator keeps the workload object (and where relevant the second Deployment) as a requirement so deleting things cannot pass.

| 3 | liveness-probe | beginner | Deployment `inventory` (2 replicas): every pod restarts about every 12s with `Liveness probe failed: connection refused`. | 4 | readiness-probe | intermediate | Deployment `catalog` (3 replicas). The app answers 503 on `/` while warming and 200 after, so a probe on `/` also works; the check accepts any probe that yields zero 503s and rejects a probe that is always true (such as `exec: true`). |
| 5 | hpa-scaling | intermediate | HPA `web-backend` (min 1, max 4, 50% CPU) shows `<unknown>/50%` and never scales, though `web-backend` (a python CPU burner pod with a `log-forwarder` sidecar) is busy. `kubectl top pods` works. | `get hpa`, `describe hpa` (`FailedGetResourceMetric ... missing request for cpu in container log-forwarder`), `top pods`, `resources.requests`, `kubectl set resources` | HPA reports a numeric CPU utilisation, condition `ScalingActive=True`, `desiredReplicas` greater than 1 within the window (the burner pushes it over 50%), HPA still targets `web-backend`, metrics-server pods untouched. | Utilisation is computed per container, so the sidecar without a request is what breaks it, while the main container already has one. Setting a request only on the main container does nothing. |
| 6 | rolling-update | intermediate | `critical-api` (4 replicas, `Recreate` strategy copied from a staging manifest) goes completely dark for 25s at every release. The release process is "push the new tag". | `get deploy -o yaml` strategy, `rollout status` during a rollout, `kubectl explain deployment.spec.strategy`, `patch` strategy type | Validator patches the pod template, then for the whole rollout polls the Service twice a second: no failed request is allowed, final state 4/4 on the new template, strategy no longer `Recreate`. | The Deployment is healthy at rest, the damage only appears during a rollout; the validator performs it. Changing only `maxUnavailable` has no effect under `Recreate` (the API rejects the combination). |
| 7 | pdb-eviction | intermediate | `kubectl drain <worker> --ignore-daemonsets` loops on `Cannot evict pod ... would violate the pod's disruption budget`. Maintenance window is open. | `drain`, `get pdb` (ALLOWED DISRUPTIONS 0), `describe pdb`, `uncordon`, eviction API behaviour | Validator drains a worker that hosts a `ledger-api` pod (with timeout), the Service never fails during the drain, the pod is rescheduled and Ready, PDB `ledger-api-pdb` still exists and still protects (disruptionsAllowed derived from a non-zero budget), then uncordons. | `--force` and `--disable-eviction` skip the PDB but drop availability, and the validator watches the Service. | 8 | blue-green | intermediate | Green release `shop-green` (3 pods, labelled `release=green`) is Running and checked. Service `shop` still sends users to blue (`release=blue`, v1). The cutover ticket says: all traffic to green, blue stays up for rollback. The Service selector reads `app=shop,version=blue`; green pods carry `app=shop,release=green` only. | `get svc -o yaml`, `get pods --show-labels`, `get endpoints`, atomic cutover by selector, keeping the old Deployment | 30/30 requests through Service `shop` return the green body, `shop-blue` still exists with its 3 pods Ready (rollback possible), endpoints equal green pod IPs. | Patching the selector to `version=green` leaves the Service with no endpoints: the key is `release` on the green side. Deleting blue passes traffic but fails the check. |
| 9 | canary | intermediate | Canary `app-canary` receives about half of the traffic of `app` (2 stable pods, 2 canary pods behind Service `app`), instead of about 10% as promised for the experiment. | `get endpoints`, `get pods --show-labels`, Service load-balancing by pod count, `kubectl scale` | Over 100 requests through Service `app` the canary share is between 1% and 25%, both Deployments exist and every pod is Ready, canary has at least 1 pod. | With plain Services, the traffic split is the pod ratio, there is no weight field. Deleting the canary gives 0% and fails the lower bound. Scaling only the canary to 1 gives 33%, which is still above the limit. |
| 10 | statefulset | intermediate | `ledger-db` runs as a Deployment (3 replicas). The replication protocol needs members named `ledger-db-0`, `ledger-db-1`, `ledger-db-2` and a stable DNS name for each, but pods are `ledger-db-6d9f...-xk2lp` and change on restart. | 11 | deployment-pause | intermediate | `frontend` was paused three days ago by someone batching changes (image `v2.4`, env `FEATURE_NEW_CART=on`). | 12 | cronjob-overlap | intermediate | CronJob `data-processor` (every minute, each run takes about 3 minutes, `concurrencyPolicy: Allow`) has piled up 4 running pods and growing; node memory is high. | `get cronjob`, `get jobs`, `get pods`, `concurrencyPolicy` options, deleting stale Jobs, `kubectl explain cronjob.spec` | At most 1 running pod owned by `data-processor`, `concurrencyPolicy` is not `Allow`, the CronJob is not suspended and exists, and a new Job was created by its schedule within the window. | Deleting only pods recreates them (the Jobs keep them). `suspend: true` stops the flood but is rejected by the check. `Replace` and `Forbid` are both accepted. |
| 13 | replicaset-orphan | advanced | After "cleaning up", `checkout-v1` Deployment is gone but 3 pods stay Running, selected by Service `checkout`, next to the new Deployment `checkout`. | 14 | maxsurge-zero | advanced | Deployment `api-server` (2 replicas, each binds `hostPort: 9000` for the node-local agent) was bumped to a new image and the rollout stalled: one new pod is `Pending: node(s) didn't have free ports for the requested pod ports`, two old pods serve. `rollout status` waits forever. | `rollout status`, `describe pod` scheduler events, `get deploy -o yaml` strategy, why surge needs spare capacity, `maxSurge` / `maxUnavailable` | Deployment `api-server` 2/2 updated on the new image and available, pods still bind hostPort 9000 (checked), rollout complete, Service answers 200 throughout the validator's rollout of one more change. | The default `maxSurge: 25%` needs a third node slot that hostPort forbids, and `maxUnavailable` rounds to 0. | 15 | statefulset-headless | advanced | StatefulSet `db` (3 replicas, `serviceName: db-hs`) has pod `db-0` Running but never Ready; `db-1` and `db-2` are never created (`OrderedReady`). ## Notes

- Shared fixtures: a `curlimages/curl:8.10.1` probe pod for validators; version bodies come from `hashicorp/http-echo:1.0` (`-text`). The python apps (l4 warm-up, l5 burner, l13 v1/v2, l15 db probe via busybox) are stdlib scripts in ConfigMaps.
- Add-on: `metrics-server` only for l5 (`requires: ["metrics-server"]`, `settle_seconds` about 45). l7 uses real node drains; the validator uncordons the node afterwards and node state reset also uncordons.
- l1 fix is creating the ServiceAccount named in the Deployment (check the ReplicaSet events); l7's PDB, l8's selector, l11's resume, l12's concurrencyPolicy, l13's ReplicaSet delete, l14's strategy numbers, l15's headless Service each end differently. l6 changes `strategy.type`, l14 changes `maxSurge/maxUnavailable` only.
- l4 and l6 validators perform a pod deletion or a rollout themselves to prove behaviour, each bounded to about 40s.
- Slugs reinterpreted: `deployment-replicas` (no replica scaling: pods never appear because of a missing ServiceAccount; scaling is used by l9 so fixes stay distinct), `maxsurge-zero` (the fix is `maxSurge: 0` for a hostPort-bound Deployment; the original "both zero" cannot exist because the API rejects it), `statefulset-headless` (headless Service with `publishNotReadyAddresses`, original Pending text was unrealistic), `replicaset-orphan` (orphan RS after `--cascade=orphan`), `rolling-update` (Recreate strategy rather than `maxUnavailable: 100%`).
- Built (l1-l8): l2 builds revisions 1-2 in setup.sh and the typo revision in broken.yaml (default 25% surge, so some old pods keep serving rather than exactly one). l7 uses its own `probe` Deployment instead of the bare fixture pod so a plain `kubectl drain` is not blocked by an unmanaged pod; its validator drains with `--pod-selector=app=ledger-api`. l3, l4, l6, l7 pods use a readiness probe and (l6, l7) a `preStop` sleep so validator results are deterministic. Fixtures: `_fixtures/probe.yaml` + `wait-ready.sh`.
- Built (l9-l15) with map changes: l9 validator samples 200 requests and also caps the canary at 15% of Ready endpoints so a 1:5 split cannot pass by luck. l10 serves each member's hostname from busybox `httpd` so `<pod>.ledger-db` is proven by the body. l11 carries the version and `FEATURE_NEW_CART` as env vars of one busybox image (no second image tag exists); the page prints `version=2.4 cart=on`. l12 builds the CronJob and four runs in setup.sh with `create job --from` (real ownerReferences); the validator waits up to about 65s for the schedule to start a run if none is active. l13 orphans `checkout-v1` in setup.sh with `--cascade=orphan`. l14 uses nginx 1.26 to 1.27 and its validator runs a second rollout while polling the Service.
- l15 redesign (maintainer decision: `publishNotReadyAddresses` belongs to module 3 l10): the members become Ready on their own, Service `db` is a normal ClusterIP Service for clients and no Service `db-hs` exists. The failure is that `db-N.db-hs` never resolves, shown by a `db-monitor` Deployment whose readiness probe wgets the three names. Fix: create headless Service `db-hs` selecting `app=db`; making `db` headless is the trap (immutable `clusterIP`, and clients lose their cluster IP, which the validator checks). The "db-1 and db-2 never created" symptom of the old row is dropped.
