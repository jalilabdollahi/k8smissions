# Module 4: storage

Teaches how pods get durable and shared files: PVC binding on the kind default StorageClass `standard` (local-path, WaitForFirstConsumer, RWO), static PVs and `claimRef`, StorageClasses, access modes, reclaim policies, StatefulSet `volumeClaimTemplates`, mount paths, `emptyDir`, ownership and `fsGroup`, and ConfigMap/Secret volumes including projection. No add-ons. Overlap decisions: m1 owns consuming ConfigMaps and Secrets as env; here they are volumes. m4 l6 owns the missing key in a volume and l13 owns projection `items`/paths. m5 owns securityContext as a hardening topic; l8 is about the ownership of files in a volume. m9 owns scheduling; the node-affinity side of local volumes appears only as a storage symptom (l3). The default StorageClass is never edited; StorageClasses a level needs are created by the player and carry the managed label. Each level has its own mechanism and fix.

| # | slug | difficulty | scenario | skills / commands | validator checks | trap or twist |
|---|------|-----------|----------|-------------------|------------------|---------------|
| 1 | pvc-pending | beginner | Deployment `orders-db` is Pending: it mounts claim `orders-db-data`, which does not exist. A similarly named PVC `orders-data` sits `Pending` (nobody uses it) and the team believes it is the culprit. | `get pvc`, `describe pod` events, WaitForFirstConsumer meaning | Pod Running with a Bound PVC at the db path; a file written through the pod survives `delete pod`; Deployment still named `orders-db`. | `Pending` on the unused PVC is normal (WaitForFirstConsumer), so players chase the wrong object. Accepts pointing at the existing PVC or creating the missing one. |
| 2 | volume-mount | beginner | `web-app` (python stdlib uploader) works, but every upload vanishes after a restart. The PVC `uploads` is mounted at `/var/uploads`; the app writes to `/srv/uploads`. | `exec ls`, `mount`/`df` inside the pod, `kubectl get pod -o yaml` | Upload via the Service, `delete pod`, upload still retrievable; PVC Bound and mounted on the path the app writes to. | No crash and no error: only the persistence test shows it. Different from l10 because a PVC already exists. |
| 3 | access-mode | intermediate | `web-servers` (3 replicas) all mount RWO PVC `site-content`, filled by a one-off Job. Two pods run on the node that owns the volume; the third sits Pending on another node ("volume node affinity conflict"). | `get pods -o wide`, `describe pod` events, `get pv -o yaml` nodeAffinity, `kubectl explain pvc.spec.accessModes` | 3/3 Ready, each serving the same `content` file from the Service over 30 requests; PVC still exactly one and RWO. | No RWX provisioner exists, so the fix is co-location (pod affinity to the same host) rather than a different access mode; lowering replicas fails the 3/3 check. |
| 4 | statefulset-volumes | intermediate | StatefulSet `postgres-cluster` (3 replicas) lists a single `persistentVolumeClaim` volume `pgdata` instead of `volumeClaimTemplates`, so pods overwrite each other's marker files and one is Pending on the wrong node. | `get pvc`, `get sts -o yaml`, `kubectl explain sts.spec.volumeClaimTemplates` | 3/3 Ready; 3 distinct PVCs `pgdata-postgres-cluster-N` Bound; each pod's marker file persists after that pod is deleted. | `volumeClaimTemplates` is immutable, so the StatefulSet has to be recreated (orphan delete) and the shared PVC removed. |
| 5 | storageclass | intermediate | PVC `reports-data` asks for StorageClass `gp3-retain`, copied from the cloud cluster. It stays Pending with "storageclass not found"; the Deployment `reporter` is Pending behind it. | `get sc`, `describe pvc`, `kubectl get sc standard -o yaml` | Pod Running; PVC Bound; its class is the one the manifest names or another class, with data surviving a pod restart. | The player creates StorageClass `gp3-retain` (provisioner `rancher.io/local-path`, WaitForFirstConsumer, `reclaimPolicy: Retain`) or edits the claim; both accepted. Cleanup lists `storageclass/gp3-retain`. |
| 6 | configmap-key | intermediate | Pod `web-app` is stuck in `ContainerCreating` since the config refactor: ConfigMap `app-config` has key `app.yaml`, the volume `items` asks for key `settings.yaml`. | `describe pod` events ("references non-existent config key"), `get cm -o yaml` | Pod Ready for 20s; the app serves the value from `/etc/app/app.yaml`; ConfigMap `app-config` still exists. | It is `ContainerCreating`, not `CreateContainerConfigError` (that is the env-var version). Either the item key or the ConfigMap is fixable. |
| 7 | secret-encoding | intermediate | `db-client` authenticates as `ledger` with a password stored in Secret `db-credentials`, but the app reports `auth failed` since the rotation: the value was generated with `echo` and carries a trailing newline, and the app compares the exact bytes. | `get secret -o jsonpath | base64 -d | od -c`, `kubectl create secret generic --from-literal` | Pod mounts the Secret and `db-client` `/status` reports `auth=ok` for 20s; secret still present and used. | `base64 -d` looks fine on screen; only `od -c` shows the `\n`. Fix is rewriting the value. |
| 8 | volume-permissions | advanced | `writer-app` runs as uid 10001 and mounts Secret `signing-keys` (`defaultMode: 0400`, root-owned) and an `emptyDir` spool. It crashes with `Permission denied` opening the key. | `logs`, `exec ls -ln`, `kubectl explain pod.spec.securityContext.fsGroup`, `defaultMode` | Pod Ready and not restarting for 30s; `id -u` in the app is not 0; app signs a payload and `/status` says `signed=ok`. | Running as root passes the crash check and fails the non-root check. fsGroup alone is not enough while the mode is 0400. |
| 9 | reclaim-policy | intermediate | The `ledger-data` PVC (PV from `standard`, default reclaim `Delete`) holds the month-end ledger. The team will rename the claim tomorrow by deleting and recreating it; a postmortem from last quarter says the data vanished that way. | `get pv -o wide`, `kubectl explain pv.spec.persistentVolumeReclaimPolicy`, `patch pv` | PV bound to `ledger-data` has policy `Retain` (the field is the outcome); pod running and ledger file intact. | The StorageClass cannot be edited, so the fix is on the PV; editing the PVC does nothing. The validator does not delete anything. |
| 10 | emptydir-vs-pvc | intermediate | `data-app` keeps customer uploads in an `emptyDir`: they survive a container crash (`kill 1`) but disappear when the pod is rescheduled or deleted. | `get pod -o yaml` volumes, `delete pod`, `kubectl explain pod.spec.volumes.emptyDir` | Upload, delete the pod, upload still there; a separate scratch dir stays `emptyDir` (not moved to the PVC). | A container restart does not lose data, so the first test misleads; only pod replacement does. |
| 11 | storageclass-mismatch | advanced | Static PV `archive-2023` (class `archive`, 50Gi, RWO) holds last year's files. PVC `archive` omits `storageClassName`, so the default class provisions a new empty volume and the pod runs happily on it. | `get pv,pvc`, `describe pvc`, `kubectl explain pvc.spec.storageClassName` | PVC Bound to PV `archive-2023`; pod `archive-reader` serves the old `2023-summary.csv`. | The PVC is Bound and the pod Running, so nothing looks broken. PVC class is immutable; delete and recreate it (and free the stray dynamic PV). |
| 12 | pv-retain | advanced | PV `billing-pv` (Retain, hostPath on a worker) is `Released` after namespace `billing-v1` was deleted; data is still on disk. New PVC `billing-data` stays Pending because the PV keeps a stale `claimRef`. | `get pv -o yaml` (claimRef), `describe pvc`, `patch pv` | PVC `billing-data` Bound to `billing-pv`; pod reads `ledger-2024.db`; PV policy still Retain. | Deleting the PV loses the pointer to the data; clearing `claimRef` is the safe move. |
| 13 | configmap-projection | advanced | `config-reader` mounts a projected volume (ConfigMap `db-config` plus Secret `db-secret`); both sources map to `path: db.conf`, so the second overwrites the first and the app reports a missing `db.password`. | `exec ls` of the mount, `get pod -o yaml` projected sources, `kubectl explain pod.spec.volumes.projected` | Both `db.url` and `db.password` readable at the expected paths; app `/status` says `config=ok`; no restarts for 20s. | The pod starts and Ready: nothing fails until the app checks both files. |
| 14 | secret-corrupt | advanced | `api-consumer` mounts Secret `api-token` with `subPath: token`. Last night the token was rotated; the Secret is correct but the pod keeps sending the old value and gets 401. | `kubectl get secret`, `exec cat`, `kubectl explain pod.spec.containers.volumeMounts.subPath` | App `/status` reports `auth=ok` and the file in the pod equals the Secret value; a second rotation done by the validator propagates to the file within the timeout. | Reinterpreted: the token is stale, not garbled. Restarting the pod passes the first check and fails the rotation check, so the mount must stop using `subPath`. |
| 15 | rwx-access-mode | expert | `ingest` (1 replica) uses PVC `shared-pvc` requesting `ReadWriteMany`; the provisioner refuses ("only ReadWriteOnce and ReadWriteOncePod supported") and the PVC is Pending. Once the claim is RWOP, a rollout to v2 hangs because the old pod still holds the volume. | `describe pvc` events, `get sc`, `kubectl explain pvc.spec.accessModes`, `rollout status`, Deployment `strategy` | PVC Bound with a single-writer mode; v2 of `ingest` rolled out, 1/1 Ready, data from v1 still present. | RWX is not available on kind; the real design is a single-writer volume. Default `RollingUpdate` deadlocks on RWOP; PVC access modes are immutable, so recreate. |

## Notes

- Fixtures: busybox and `python:3.12-alpine` apps with stdlib `http.server` and a `/status` endpoint; probe pods are `curlimages/curl`; seed data written by a one-off Job or `setup.sh`. Nothing touches StorageClass `standard`.
- Honest kind limits: no RWX provisioner, so l3 is solved by co-location and l15 by single-writer design; the map says so in the debrief. l15 depends on local-path-provisioner accepting `ReadWriteOncePod`; confirm on the pinned version, else use RWO with a node-bound deadlock via `nodeSelector` as fallback.
- Slugs reinterpreted: l7 `secret-encoding` (trailing newline instead of an audit finding about base64), l14 `secret-corrupt` (stale value through `subPath` instead of a garbled one), l15 `rwx-access-mode` (RWX request becomes RWOP plus rollout strategy), l12 `pv-retain` (stale `claimRef` on a Released volume), l11 `storageclass-mismatch` (silent default-class provisioning).
- PVs and StorageClasses created in broken.yaml carry the managed label so the engine deletes them between levels; hostPath PVs use a per-level directory.
