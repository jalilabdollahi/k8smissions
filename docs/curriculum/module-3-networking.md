# Module 3: networking

Teaches how traffic finds pods: Services in depth (selectors, NodePort, `externalTrafficPolicy`, session affinity, headless, multi-port, `LoadBalancer` on a cluster without a cloud), cluster DNS from the client side, Ingress with ingress-nginx, and NetworkPolicy ingress and egress (kindnet enforces policy). Add-on: `ingress-nginx` for levels 4, 14 and 15 (set `requires`). Overlap decisions: m1 owns "Deployment selector vs template labels" and "port vs containerPort", so l1 here is a Service selector that matches too much, not too little. m2 l15 owns the basic headless Service for a StatefulSet, so l10 is about discovery before readiness. m5 l4 owns NetworkPolicy as isolation, so l5 and l12 are about a policy that blocks legitimate traffic. m6 owns probe design, so l8 is about the endpoint consequence of a probe whose dependency is broken. m11 owns ndots and node-local DNS cost, so l3 is about pod DNS policy only. Every level has its own failing mechanism and a different final fix.

## Notes

- Fixtures: probe pods use `curlimages/curl`; backends are `nginx:alpine` with ConfigMap `default.conf`, `hashicorp/http-echo`, or `python:3.12-alpine` scripts; nothing custom. ingress-nginx is reached through its controller Service inside the cluster, never through host ports.
- Honest kind limits: l9 teaches that `<pending>` never resolves without a cloud controller; the working path verified is the NodePort. l13 and l12 rely on kindnet semantics (NodePort source IP, post-DNAT policy matching) that must be confirmed on a test cluster before the level is written; the map names the fallback.
- Slugs reinterpreted: l8 `endpoints` (original was "some requests fail"; now empty endpoints from a sidecar-gated probe), l10 `headless` (publishNotReadyAddresses instead of plain headless, which m2 l15 owns), l14 `ingress-defaultbackend` (class mismatch plus default backend), l9 as above.
- Second-half verification on kind (kindnet, ingress-nginx): (l12) egress policies match the post-DNAT pod, so allowing CoreDNS and the DB by pod selector works as designed. (l13) from an ordinary pod, NodePort traffic with `Local` is treated as in-cluster and is not dropped or source-preserved reliably, so the level uses a host-network client `gw-client` on the control-plane node as the "external" caller; `Local` then drops on the pod-less worker and preserves the caller node IP, `Cluster` masquerades it. The validator compares the echoed address with `gw-client`'s node IP instead of a probe pod IP, and the two pods start co-located by a leftover `podAffinity` (fix: topology spread; scaling alone does nothing). (l14) ingress-nginx does NOT use `spec.defaultBackend` for unknown hosts when the same Ingress has rules; it does when the Ingress has only a `defaultBackend` (no rules), or a host-less rule. The level keeps the class fault and makes the second half "put the fallback in its own Ingress"; any of the three forms passes. (l10) uses `podManagementPolicy: Parallel` so the pods start together and the only deadlock is DNS. (l11) setup.sh rolls out release 4.1 first so a rollback has real history, and the validator requires the 4.2 body.
